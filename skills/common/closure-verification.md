# 通用闭环验证口径（共享参考）

> 本文件是多个 pentest 技能共用的「闭环验证 / 判定分级」通用口径，供技能正文指向后用 read_file 读取。
> 它**不是一个独立技能**（非 SKILL.md，不会进入技能表）。各漏洞的「实际效果验证方向」「漏洞特有的闭环要点」仍由各技能正文自行给出。

## 闭环验证要求（必须遵守）

- 所有结论必须形成「前置条件/输入 → 系统处理 → 实际效果/危害 → 可复核证据」的完整证据链，重点证明风险真实生效，而不是只看响应。
- 仅凭上传成功、请求成功、状态码变化、单次报错、配置落盘、前端提示、登录跳转、返回文案等中间信号，不得直接判定 `confirmed`。
- 若只有中间信号、缺少真实效果/危害验证，结论最多为 `suspected`。
- 对写操作、上传、配置变更、认证命中、权限变更、解析触发等场景，必须补做访问、回读、触发、解析、执行或副作用验证，证明风险真正落地并说明具体危害。
- 无法闭环时，必须明确缺失环节与下一步验证建议，不得跳过验证直接下结论。

## 取证完整性（必须遵守）

证据链里引用的东西必须是你**真实看到过**的，不得虚构或想当然：

- 引用的每段源码 / 配置 / 类名 / 字段名 / 黑名单内容，必须出自你实际打开读过的文件，并标注 `file:line`；**禁止凭印象或推测编造**一段"看起来该是这样"的代码、类名或字段。
- 反编译产物（如 `.class` 反编译、闭源 jar）、第三方依赖、运行时动态生成的内容，引用时必须**标注其来源与不确定性**（如"反编译自 xxx.class，方法名可能经混淆"），不得伪装成项目源码。
- 引用的请求 / 响应 / 命令输出必须是真实发出并捕获到的，能在流量/日志中回溯到对应记录；不得贴一段"理想化"的、实际从未发送或从未收到的请求/响应当作证据。
- 凡是无法定位到真实出处的引用，要么补到能定位、要么删去，**绝不允许用编造的证据支撑任何结论**——编造证据比漏报危害更严重。

## 判定分级语义（通用）

下表中 `confirmed / suspected / not vulnerable` 是**判定语义**（技能正文、思考、回填白盒候选时用的词）。**注意它不是 jsonl `status` 字段的取值**：报告模板里 `status` 的合法取值集合由所选模板的"发现记录"节定义（见 result-with-file），模板里**通常没有 `suspected` 这个词**。把判定语义词原样写进 `status` 会让该发现匹配不到任何归档桶而被**静默丢条**，违反「欠覆盖优于误删」。落库时按"归档桶"映射，不要照抄判定词：

| 判定语义 | 含义 | 落库归档桶（`status` 取模板里该桶对应名） |
|------|------|------|
| `confirmed` | 已用完整证据链证明真实危害/能力确实生效（读到真实数据、写操作回读生效、命令执行结果可复核等）。 | 进正文·**已确认**档（当前模板名 `confirmed`） |
| `suspected` | 只有中间信号（状态码、报错、前端提示、响应差异）或仅静态候选，尚未证明真实危害。 | 进正文·**待复核**档（当前模板名 `needs_review`）——**绝不丢条** |
| `not vulnerable` | 防护生效、无敏感数据泄露或越权效果（如稳定 401/403、无泄露的 404）。 | **覆盖证明**档（`not_vulnerable`）或**排除项**档（`false_positive`） |

> 口径：判定上**宁可标 `suspected` 也不夸大 `confirmed`**；落库时 `suspected` 归入"待复核"档留在正文，**降级 ≠ 删除**。具体 `status` 字面值以所选模板为准，不确定就读模板的"发现记录与派生"节。

## 通用误报控制

- 不以单一状态码定论，必须看响应体真实业务字段或可观测副作用。
- 写操作以持久化回读结果为准，不以接口即时回包单独定论。
- 对可能命中缓存/降级模板的响应，追加一次带随机参数的复验。

# 反编译 triage 决策详表

> 主文件 `SKILL.md` 只保留 triage 概述（判定维度 + 主要分支）。本文件展开完整决策细节，供需要时按需 `read_file` 加载。
>
> 核心立场：**绝大多数依赖不需要反编译**。要么是行为已知的常见公共库、要么能直接取到官方源码——这两类都不反编译。反编译有成本，产物带混淆不确定性，只对"落在关键路径上、又取不到源码、安全/sink 决策发生在它内部"的少数依赖才做。

## 决策维度（顺序仅作建议，可按现场调整）

按从便宜到贵的顺序判断：命中某个维度可直接定动作，避免推进到更贵的维度。

### 维度 1：是否行为已知的常见公共库

- 例：Spring、Jackson、fastjson、commons-*、Netty、lombok 等
- 命中 → **不反编译**：按已知语义推理其 source/sink/副作用；关注其已知漏洞交 [dependency-audit](../../dependency-audit/SKILL.md) 查 CVE
- why：行为有公开文档与社区共识，反编译只会增加噪声

### 维度 2：本机是否已落盘有现成源码（0 外联）

只翻本地缓存，不联网：

- Java：`find ~/.m2 ~/.gradle -name '*-sources.jar' 2>/dev/null` 查本地缓存；jar/war 同目录、`WEB-INF/lib` 旁、解包目录里找配套 `-sources.jar`
- Python：很多 wheel/包目录里直接带 `.py` 源（非纯 `.pyc`），优先读这些
- JS：包内随附的 `.map` source map、或未压缩（非 `.min`）的发布文件
- native / .NET：随附调试符号（`.pdb` / DWARF）

有 → **取源码，不反编译**（官方/原始源码无混淆、名/行号可信，优先级高于反编译产物）
本地没有 → 暂不联网取件，继续往下走维度 3/4 定性与决策点

### 维度 3：常见公共库还是非公共库（轻量探查）

仅凭名称/坐标分不清是常见库还是私有封装，按从便宜到贵的顺序定性：

**便宜信号**（不碰 jar）：
- `rg '^import' 项目源码` 看实际引用了哪些外部包、用在哪、被多少文件引用
- 包名前缀：`org.<项目名>.*` / `com.<公司名>.*` 等非知名命名空间多为非公共封装；`org.apache.*` / `com.google.*` / `org.springframework.*` 是公共库
- **starter 盲区**：Spring Boot starter 自动注册自带 controller/endpoint，逻辑在 jar 内、项目源码看不到对应 import——这类要结合入口点/框架枚举判断，别只按 import 数定攻击面

**jar 内廉价元信息**（全离线）：
- `unzip -p x.jar 'META-INF/maven/*/pom.properties'` 取 `groupId/artifactId/version`（定坐标金标准）
- `META-INF/MANIFEST.MF` 的 Vendor / Implementation-Title 辅证

**仍拿不准**：用 `javap -p` 或只反编译几个代表性类速看（不整包反编译）：
- 是常见库 → 回维度 1 处理
- 非公共库、无源码 → 进维度 4

### 维度 4：非公共库 + 取不到源码 → 三步判定

#### 4.1 关键路径判定（否决性筛子）

**关键路径判定只能用外部可证事实**——即"数据流确认无污点跨入" + "正面证明依赖只是标准化数据/协议通道（如 JDBC 驱动）"。

**why 不能用"消费侧没看到 import / 看不见内部"判定**：入口点与信任边界逻辑（starter 自动注册的 controller、自研 filter/拦截器打进 jar、编程式注册的 route）封在产物内部、消费侧不可观测，用消费侧分析下"不在关键路径"是循环依赖。

| 判定 | 处置 |
|---|---|
| 外部可证不在关键路径（数据流确认无污点途经、正面证明只是标准化通道） | 不反编译 |
| 同厂商自有闭源（入口点封在产物内、消费侧不可观测） | **归属即触发查证**，归候选——不要求先证它在关键路径 |
| 第三方异厂商商业的"位置拿不准" | 偏放行当候选 |

**攻击面可见性不对称**（贯穿三个触发面的关键判据）：
- 触发面 3（数据流污点）的"污点跨入依赖"**外部可观测**——调用点能看到污点进了哪个依赖
- 触发面 1/2（入口点/信任边界）的逻辑**封在产物内部、消费侧 import 看不见**

对同厂商自有闭源，"用消费侧 import 证明它不在关键路径"是循环的——不打开就证不了，故归属本身即触发查证。

#### 4.2 决策点 (a)/(b) 判定（反不反编译的真正开关）

判据**核心是"安全/sink 判定发生在依赖内部、还是在调用方代码里"——看决策点在哪，不是看它标不标准**。

**(a) 决策在调用方，依赖只是被调用的标准化数据/协议通道**：
- 例：JDBC 驱动——在 SQL sink 路径上，但"拼什么 SQL、用不用参数化"的决定在调用方，驱动只按 JDBC 规范执行
- 处置：依赖本身不是"需看内部的目标面"，靠已知语义/文档/CVE 说清即可、不反编译且不留缺口
- **举证责任**：判 (a) 的依据是"正面证明决策在调用方"（已知语义/标准规范/CVE 可佐证），不是"廉价扫描没扫到入口点/安全逻辑"——后者证不了它不是 (b)

**(b) 安全/sink 决策发生在依赖内部**：
- 例：鉴权/授权/路由/过滤/sink 判定在 jar 里完成
- 处置：不看内部就不知道它实际怎么判，"行为已知"不成立——**须看清内部**（取到 sources 则读源码、取不到才反编译）
- **闭源组件即便自称实现标准协议**（如某商业 OAuth/JWT 校验 jar、标准协议的鉴权 SDK），只要授权决策在它内部，就是 (b)——"协议标准"不等于"已知它真按标准做了、没夹私货或后门"

**与归属无关**——同厂商还是第三方都按 (a)/(b) 判。

#### 4.3 归属调节（影响优先级与法律谨慎，不改 (a)/(b) 结论）

用极低成本读取定归属：
- `unzip -p x.jar META-INF/MANIFEST.MF` 看 `Implementation-Vendor`/`Vendor`
- `pom.properties` 的 `groupId` 是否 = 项目自身前缀/项目私服（如自研 nexus）
- 包内 `LICENSE`/`NOTICE` 是否标第三方商业或专有许可（如 BCL、达梦专有）

| 归属 | 处置 |
|---|---|
| **同厂商自有**（含同厂商自研的商业闭源） | 归属即触发查证（候选），不要求先证在关键路径——反编译主战场，优先且无法律顾虑；要免（落 (a)）须正面举证决策在调用方 |
| **第三方异厂商商业闭源** | 同样按 (a)/(b) 判：(a) 可免；(b)（含 OEM/低代码平台承载鉴权路由、自称标准协议的闭源鉴权 SDK）则反编译并标**法律风险（EULA 可能禁逆向）**与不确定性 |
| **归属 `unknown`**（Vendor/坐标缺失、拿不准）且在关键路径 | 偏放行当候选去看，不要因为定不了归属就掉进缝里跳过 |

## 关键约束（与捷径边界同口径）

- 关键路径上落 (b) 的依赖、以及同厂商自有闭源归属即候选但未查清内部（既未完整排除入口点、也未正面证明落 (a)）的：若选择不反编译，等于没看它内部 → 那条穿过它的污点/攻击面问题须留 `needs_review`/显式缺口交回上游，不能用"走 CVE / 行为已知"假性闭环冒充安全
- CVE 扫描只覆盖"已知漏洞"，不覆盖"这个闭源组件在我污点路径上实际做了什么"；对 (b) 类，下"not_vulnerable"的前提是已反编译并读过目标面
- **(a) 豁免按当前污点/sink 问题限定**：只是说"在这条链上它不是决策者"，不等于该闭源依赖全局可信——它是否被投毒/夹后门/有额外外联是另一类威胁（供应链），归 [dependency-audit](../../dependency-audit/SKILL.md)/SCA 查 CVE 与来源

## 快捷判定矩阵（极低成本信号 → 一眼定动作）

| 信号（成本极低） | 判定 |
|---|---|
| `pom.properties` 命中公共坐标 / 包名 `org.apache.*`·`com.google.*`·`org.springframework.*` | 公共库 → 不反编译 |
| 本地缓存或包内有配套 `-sources.jar` | 取源码 → 不反编译 |
| 本地无 jar/源码 + 须看内部（自有闭源归属即触发、不要求先证 (b)；第三方落 (b) 才触发） | 按坐标取件（捷径 D）：sources 优先 → 失败取 plain jar 反编译 → 仍失败 `needs_review` |
| 包名私有前缀 `org.<项目>.*`·`com.<公司>.*` 且无公共坐标 | 非公共库 → 须按 Vendor/坐标二次定归属；落同厂商自有闭源即候选查证（归属即触发、不要求先证在关键路径）；要免须正面证明它是落 (a) 的纯标准化通道，不靠"没扫到"放行 |
| `MANIFEST` Vendor / `pom` groupId = 项目自身前缀或同厂商私服 | 同厂商自有闭源 → 归属即候选查证；仅当正面证明落 (a) 才免反编译 |
| `MANIFEST` Vendor / 坐标 = 外部厂商 + 商业/专有许可（BCL、专有等） | 第三方异厂商商业 → 不在关键路径、或在关键路径但落 (a) 则免反编译（走 dependency-audit）；落 (b) 则反编译并标法律 |
| 类名 `a.a.a`/`o0Oo` + 字符串常量被加密/缺失 | 混淆 → 是强信号但不是开关；仍按重要性 + 决策点 (a)/(b) 定、归属调节，关键路径上落 (b) 要看的才上 `--deobf` |
| import 计数高且在 sink/入口点附近 | 攻击面大 → 优先 |
| import 计数低但 `spring.factories` 注册了 Controller | starter 盲区 → 仍要看 |

## 捷径的边界：定性可抽样，定论必须覆盖重点

捷径帮**快速找到该看的**，不是**少看**的借口。抽样 / 单类反编译 / `javap` 速看只支持「路由定性」——判断是不是自研、要不要继续深挖；**不支持下否定结论**。四条闸门：

1. **"非漏洞 / 行为安全 / 无此能力"的否定结论**：前提是已把触发本次恢复的目标面完整反编译并读过——那个入口点 handler、命中的 sink 类、信任边界上的鉴权/过滤/加解密逻辑所在类及其调用链；目标面没覆盖到就没有资格判 `not_vulnerable`
2. **"jar 内无入口点 / 无安全决策 → 免反编译"的否定结论，不能靠廉价信号扫描为空**：`spring.factories`/`META-INF/spring imports`、`javap -v` 注解、`strings` 对"找到入口点"是强信号、对"证明没有入口点"是弱信号——程序化注册、消费方 `@ComponentScan` 扫到 jar 内包、非注解路由都绕过这些廉价信号
3. **自有闭源要"免"，门槛严格的两条之一**（纯 util 也不例外）：
   - (1) 完整覆盖入口点机制：`spring.factories`/`*.imports` + 全类注解枚举（`javap -v` 遍历，非抽样）+ 程序化注册搜索（`rg` 找 `registerBean`/`addHandler`/`ServletContext`/`@ComponentScan` 命中包等）都做过、能正面排除自注册入口点
   - (2) 从调用方侧正面证明它落 (a)（决策在调用方、依赖仅被当标准化通道调用）

   两条都不满足 → 不据"没扫到"放行，自有闭源回到"归属即候选查证"，继续覆盖到能排除为止、否则留缺口

   **(a) 不覆盖"自带入口点"维度**：一个 jar 可能既没被当 sink 调用（谈不上 (a)/(b)）、又自注册 web 入口点，这种只能靠 (1) 排除
4. **覆盖不全 / 反编译失败 / 关键字符串被加密解不出 → 判 `needs_review`**，并写明"已覆盖 X、未覆盖 Y、缺失原因"，把未覆盖目标当作缺口交回上游继续追

## 一句话收口

**捷径帮你"快速找到该看的"，但"该看的"必须真看到**；快不等于可以漏，欠覆盖优于误判无害。
